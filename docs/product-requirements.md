# 综合 C++ IDE：产品定位与总体需求

## 一、产品定位

开发一款面向 C++ 开发者的综合型 IDE，以竞赛编程场景下的轻量、快捷、低配置、低资源占用体验为核心，同时通过插件系统提供可扩展的工程开发能力。

产品采用单一版本、统一架构，不区分竞赛版和工程版，不通过维护两套产品来满足不同用户的需求。

**核心负责提供完整、可靠、轻量的 C++ 开发体验；插件负责扩展核心之外的专业能力。**

用户安装 IDE 后，无须创建工程、配置复杂的构建系统或安装任何插件，即可打开单个 `.cpp` 文件，完成编辑、编译、运行、调试和测试。

当用户需要大型工程开发、完整语言服务、版本控制、依赖管理、静态分析、远程开发等能力时，可以按需安装相应插件。

插件不是核心功能的替代品，也不是必须安装的组件。它们应当在不破坏核心体验的前提下，为 IDE 提供渐进式扩展能力。

产品的最终目标是：**不安装插件时，它是一款完整、顺手的轻量 C++ 竞赛 IDE；安装插件后，它可以逐步扩展为覆盖专业工程开发场景的综合 C++ 开发环境。**

---

## 二、核心设计原则

### 2.1 单一产品，统一架构

整个产品只维护一个 IDE、一套核心和一套产品路线。

竞赛编程与工程开发是同一款 IDE 的不同使用场景，而不是两款独立产品。

不得为了实现工程能力而引入独立的工程版，也不得让核心逐渐演变成必须依赖大型工程系统才能正常工作的重量级 IDE。

### 2.2 核心完整，插件可选

核心必须能够独立完成日常 C++ 开发和竞赛编程所需的主要工作。

包括但不限于：

- 编辑代码。
- 编译和运行。
- 输入输出管理。
- 样例测试与批量测试。
- 特殊测试数据管理。
- 对拍。
- 基础调试。
- 基础代码智能感知。
- 自动保存与崩溃恢复。

这些功能不能被拆分成必须额外安装的插件。

插件主要负责扩展专业能力，而不是人为制造核心功能缺口。

### 2.3 轻量优先，按需扩展

轻量不是单纯追求安装包小，而是要求核心在启动速度、内存占用、CPU 使用、磁盘访问和后台任务方面保持克制。

未安装的插件不得参与启动流程。

已安装但未启用的插件不得运行后台任务。

已启用的插件也应当按需加载，避免仅仅因为安装了某项功能，就持续消耗资源。

核心不应为了预留所有工程能力而引入庞大的常驻服务。

### 2.4 单文件工作流优先

单文件开发是核心工作流，而不是工程开发模式的简化版。

用户打开一个 `.cpp` 文件后，应当可以直接编译、运行、查看错误和进行调试，不必创建项目、不必生成配置文件，也不必理解 CMake 等构建系统。

用户可以主动将单文件工作流升级为多文件或工程工作流，但 IDE 不得强迫用户这样做。

工程插件不能改变这一原则。

### 2.5 工具中立，不预置算法

IDE 提供编辑、编译、调试、测试、格式化和扩展能力，不负责向用户提供预先编写好的算法答案。

不得内置数学、图论、数据结构等分类的算法模板，也不得预置算法代码片段库。

模板和代码片段系统应当作为用户可管理的工具存在，支持创建、编辑、导入和导出，但不附带官方算法内容。

AI 插件同样遵循这一原则：以解释、提示、诊断和辅助理解为主要定位，不默认生成整段算法解法。

### 2.6 稳定性优先于功能数量

IDE 的核心编辑、编译、运行和调试流程必须具有明确的失败处理机制。

任何插件异常、语言服务卡死、编译失败、程序死循环或输出爆炸，都不应导致核心编辑器整体失去响应。

功能可以逐步增加，但不能以牺牲基础工作流的可靠性为代价。

## 三、核心 IDE 的功能范围

以下功能属于核心产品，不依赖任何插件。

### 3.1 代码编辑

提供完整、轻量的 C++ 编辑体验，包括：

- 多文件标签页。
- 语法高亮、括号匹配和自动缩进。
- 代码折叠。
- 查找、替换和跳转行。
- 多光标与列编辑。
- 基础补全和语法检查。
- 基础符号识别、跳转与重命名能力。
- 格式化接口及可选的基础格式化实现。
- 字体、字号、主题、配色和缩放设置。
- TODO 标记、书签和可配置快捷键。

补全、语法分析和高亮应当具有相互独立的启停设置。

关闭补全，不得同时关闭语法高亮或其他独立的分析功能。

高级跨文件语义分析可以交给工程插件，但基础编辑能力必须由核心保证。

### 3.2 单文件编译与运行

打开 `.cpp` 文件后，应当可以直接执行：

- 一键编译。
- 一键运行。
- 编译并运行。
- 重新运行上次程序。
- 查看编译错误和警告。
- 双击错误信息跳转至对应代码位置。

核心应当能够自动发现可用编译器，并允许用户手动指定编译器路径、编译参数和运行环境。

编译器不存在或配置错误时，必须明确提示原因，不得表现为按钮无响应。

实际编译命令、运行命令、工作目录、环境变量和程序参数必须可以查看，不能将关键执行过程隐藏为黑盒。

### 3.3 输入输出管理

核心应提供统一的输入输出管理界面，支持：

- 标准输入。
- 从文件读取输入。
- 将输出写入文件。
- 样例、自定义输入和文件输入之间快速切换。
- 分别查看 stdout 与 stderr。
- 查看运行耗时、退出码和运行状态。
- 控制输出显示上限。
- 复制和保存运行结果。

输入输出面板应当适合竞赛编程场景，并允许用户调整字体、字号、缩放和显示布局。

复制、粘贴等操作不能依赖右键菜单，必须提供明确、可靠的快捷键或其他可访问方式。

### 3.4 样例测试与测试数据管理

核心应提供独立的测试系统，而不是将测试功能简单实现为运行按钮的附属操作。

支持：

- 多组输入与期望输出。
- 多组样例批量执行。
- 输出差异比较。
- 测试结果汇总。
- `.in` 与 `.out` 文件导入。
- 测试点分组。
- Subtask 分组。
- 指定测试点运行。
- 失败测试一键复现。

测试结果应当明确区分编译失败、运行错误、超时、输出超限和答案不一致等情况。

对于失败测试，应尽可能保留必要的输入、输出、运行参数和错误日志。

### 3.5 对拍系统

对拍是核心的一等功能，不应被设计成普通测试功能中的隐藏选项。

用户可以指定：

- `sol.cpp`：待验证的正式解法。
- `brute.cpp`：暴力或参考解法。
- `gen.cpp`：数据生成程序。

并设置对拍轮数、超时时间、输出上限及其他必要的运行参数。

系统应当能够自动编译相关程序、循环生成数据、分别执行解法并比较输出。

出现差异或运行异常时，应立即停止对拍，保存失败输入、相关输出和必要日志，并提供一键复现入口。

对拍期间应清晰展示当前轮数、运行状态和失败原因。

多文件标签页应能明确展示各文件在对拍任务中的角色，避免将生成器、正式解法和暴力解法混淆。

### 3.6 运行隔离与资源控制

程序运行必须与 IDE 核心进程保持适当隔离。

核心应提供统一的运行管理机制，并支持可配置的：

- 时间限制。
- 内存限制。
- 输出限制。
- 超时终止。
- 子进程清理。
- 运行状态监控。

对于死循环、无限输出、异常退出和子进程残留等情况，应当能够及时停止运行并回收相关资源。

不得仅依靠终止直接子进程来假定整个进程树已经结束。

对于栈溢出、内存耗尽等异常，应尽可能识别并提供明确的错误信息。

需要注意，具体的内存限制、进程隔离和强制终止能力取决于操作系统及其提供的机制。实现时必须明确平台支持范围，不得将无法保证的限制描述成绝对安全的沙箱。

### 3.7 基础调试

核心提供轻量级 GDB 调试能力，至少支持：

- 设置和管理断点。
- 单步执行。
- 步入、步过和继续运行。
- 查看变量。
- 查看调用栈。
- 求值表达式。
- 调试输入重定向。
- 停止调试和清理调试进程。

GDB 不存在、启动失败、调试协议异常或目标程序无法正常启动时，应显示明确日志。

基础调试属于核心能力。更完整的多线程、寄存器、反汇编和复杂内存检查等专业调试能力，可以通过插件扩展。

### 3.8 配置、恢复与便携

核心应支持：

- 自动保存。
- 异常退出后的未保存内容恢复。
- 崩溃日志。
- 可配置的编译器与运行环境。
- 用户自定义模板。
- 用户自定义代码片段。
- 主题、字体、快捷键和配色配置。
- 配置导入与导出。
- 离线运行。
- 绿色便携部署。

便携模式应允许用户将 IDE、编译器、必要工具和个人配置放在指定目录中整体携带。

不得强制要求联网、注册账户或使用云端服务才能完成基础 C++ 开发。

## 四、模板与代码片段系统

模板和代码片段应当提供管理能力，而不是提供算法内容。

### 4.1 模板

默认不预置算法模板。

可以提供一个极简空白代码骨架，也可以在首次启动时允许用户自行创建或粘贴模板。

用户能够创建、编辑、删除、导入、导出和切换自己的模板。

模板系统不应限定用户只能创建一套模板，但默认界面应保持简洁。

### 4.2 代码片段

核心提供空的代码片段管理器。

用户可以自行创建、分类、编辑、导入和导出代码片段。

不得预置算法片段库，也不得通过官方模板、示例工程或内置代码向用户提供成套算法解法。

**产品原则：提供容纳用户知识的工具，不代替用户准备知识本身。**

## 五、插件系统

插件系统是产品的基础架构组成部分，而不是后期附加的功能。

由于大量专业工程能力需要通过插件提供，插件系统必须具备清晰的接口、生命周期、资源管理、权限控制和故障处理机制。

### 5.1 插件 API

核心应提供稳定、版本化且文档化的插件 API。

至少覆盖以下能力：

1. 编辑器扩展。
2. 文件与工作区访问。
3. 编译与构建任务。
4. 程序运行与沙箱管理。
5. 调试器接入。
6. 测试框架接入。
7. 配置管理。
8. 日志与诊断。
9. 菜单、工具栏、面板和其他 UI 扩展点。
10. 任务调度与进度反馈。
11. 插件间的有限协作机制。

API 必须明确每项能力的输入、输出、错误处理方式、生命周期和兼容性要求。

插件不应直接依赖核心内部实现，也不应通过修改核心文件或注入未公开接口来实现正常功能。

核心 API 应具有明确的版本兼容策略，避免一次核心升级导致大量插件无法使用。

### 5.2 插件生命周期

至少支持：

- 安装。
- 启用。
- 禁用。
- 卸载。
- 升级。
- 版本检查。
- 依赖检查。
- 兼容性检查。
- 故障诊断。

用户应能查看插件名称、版本、状态、依赖、权限和错误日志。

插件升级失败时，应尽可能保留原有可用版本或提供恢复途径。

### 5.3 加载与资源管理

插件应按需加载。

未安装的插件不应产生任何运行开销；已安装但未启用的插件不应启动服务或执行后台任务。

启用插件后，也应尽可能推迟重量级组件的初始化，直到用户真正使用相关功能。

插件应明确声明所需资源和后台任务，并允许核心管理其启动与停止。

不能仅通过将所有功能移入插件目录，就宣称实现了轻量化。必须实际验证插件对启动时间、内存占用和后台资源的影响。

### 5.4 故障隔离与降级

插件崩溃、超时或 API 调用失败时，核心必须能够检测并处理异常。

插件故障不应导致编辑器、文件保存或核心编译运行流程整体崩溃。

对于可能卡死或消耗大量资源的插件任务，应提供取消、超时和资源回收机制。

需要特别区分进程隔离与普通异常捕获：如果插件能够执行任意原生代码，就不能仅靠捕获异常来保证其不会破坏核心进程。

因此，插件运行模型应根据风险分级设计：

- 轻量 UI 扩展可以使用受控的进程内机制。
- 复杂语言服务和重量级后台任务应优先考虑独立进程。
- 具有较高权限风险的插件应使用更严格的权限限制和隔离机制。

具体采用进程内插件、独立进程或混合架构，应在技术设计阶段确定，不能只停留在概念层面。

### 5.5 权限与安全

插件必须遵循明确的权限模型。

应能够向用户说明插件是否需要：

- 读取或修改项目文件。
- 启动外部程序。
- 访问网络。
- 访问凭据或其他敏感配置。
- 执行后台任务。
- 调用调试器或其他系统工具。

不得默认允许插件不受限制地访问所有资源。

插件不得偷偷上传源代码、测试数据、运行日志或其他用户文件。

需要网络访问的插件应明确说明用途；核心不得强制联网。

同时，应明确插件权限机制的实际边界：未经操作系统隔离的原生插件通常具有较高权限，不能仅通过 UI 权限声明就获得可靠的安全隔离。

### 5.6 安装方式

至少支持从本地插件包安装插件。

插件包应包含必要的元数据，例如：

- 插件标识。
- 名称与版本。
- 核心 API 兼容范围。
- 平台与架构要求。
- 依赖项。
- 权限声明。
- 入口与资源清单。

插件市场可以后续建设，不应成为插件系统投入使用的前置条件。

离线环境中，用户仍应能够安装已经获得的本地插件包。

### 5.7 配置与诊断

支持导出和导入插件清单、版本信息及插件配置，以便迁移环境或恢复便携式开发环境。

导出配置时，应避免默认打包 API Key、密码和其他敏感凭据。

核心应提供统一的插件日志与诊断入口，清晰记录加载失败、API 不兼容、依赖缺失、任务超时和插件崩溃等问题。

## 六、工程开发能力插件

工程能力统一通过插件扩展，不单独开发工程版，也不要求所有用户安装完整插件集合。

以下是建议的插件能力方向，不代表所有插件必须在首个版本同时完成。

### 6.1 工程构建

支持 CMake、Make、Ninja、Bazel 等构建系统，以及多目标、多配置和复杂工程结构。

### 6.2 完整语言服务

支持 `compile_commands.json`、clangd、跨文件语义分析、引用查找、符号跳转和更完整的重构能力。

### 6.3 版本控制

提供 Git 状态查看、差异比较、提交、分支管理、冲突处理和历史浏览等功能。

### 6.4 专业调试

扩展线程管理、Watch、寄存器、反汇编、Core Dump、内存检查及更复杂的调试工作流。

### 6.5 测试与质量分析

支持单元测试框架、测试发现、测试报告、覆盖率展示，以及 clang-tidy、cppcheck 等静态分析工具。

### 6.6 Sanitizer 与运行时诊断

提供 ASan、UBSan、TSan、MSan 等工具的配置、运行和结果展示。

具体工具的可用性应根据编译器、运行平台和工具链能力判断。

### 6.7 依赖管理

集成 vcpkg、Conan 等依赖管理工具，支持依赖配置、安装、更新和诊断。

### 6.8 远程开发与容器环境

支持 SSH、WSL、Docker、Dev Container 等远程或隔离开发环境。

### 6.9 交叉编译与嵌入式开发

支持额外工具链、目标平台、交叉编译配置以及嵌入式开发工作流。

### 6.10 性能分析

根据平台和工具可用性，集成 perf、Valgrind、VTune、Tracy 等性能分析工具。

### 6.11 团队与 CI 能力

按需提供代码审查辅助、CI 结果回显、构建诊断、团队工作流集成等扩展能力。

## 七、AI 功能的边界

AI 不应成为核心 IDE 的强制组成部分。

如未来提供 AI 插件，应满足以下要求：

- 默认关闭或由用户主动启用。
- 不依赖 AI 才能完成基础编译、运行、测试和调试。
- 支持明确的联网开关和数据使用说明。
- 不默认上传整个项目。
- 不预置算法答案或自动生成整段竞赛解法。
- 主要提供错误解释、概念提示、代码诊断和学习辅助。
- 用户可以随时禁用或卸载 AI 插件。

AI 插件必须遵循与其他插件相同的权限、隔离和资源管理原则。

## 八、关键问题与专项验收

以下问题应作为产品设计和测试阶段的重点，而不是开发结束后的普通优化项。

### 8.1 基础交互可靠性

重点验证：

- 点击编译或运行后没有响应。
- 调试启动失败或异常退出。
- 停止程序后仍有子进程残留。
- 调试控制台无法可靠复制和粘贴。
- 字体缩放后运行结果错位。
- 高 DPI 下界面模糊或布局异常。
- 关闭补全后其他编辑能力意外失效。

### 8.2 执行过程透明

编译、运行、调试和测试任务都应具有明确的状态反馈。

用户应能查看实际命令、参数、工作目录、环境变量和日志。

任何失败都应尽可能给出具体原因，而不是只显示通用错误提示。

### 8.3 核心性能

建立不安装插件时的基准测试，至少记录：

- 冷启动时间。
- 空闲内存占用。
- 打开大型源文件的耗时。
- 首次编译与运行的响应时间。
- 常见操作的响应时间。

后续安装或启用插件时，应对照基准评估额外开销。

性能目标应在技术选型和原型测试阶段确定，并在不同硬件条件下验证。

### 8.4 插件故障测试

应模拟插件加载失败、API 版本不兼容、后台任务卡死、异常退出和资源耗尽等情况。

验收重点是：核心能够检测故障、终止相关任务、提供日志，并尽可能恢复正常工作。

### 8.5 单文件工作流测试

这是产品的关键验收场景。

在全新安装、未安装插件的环境中：

1. 启动 IDE。
2. 打开一个 `.cpp` 文件。
3. 直接编译并运行。
4. 输入自定义数据。
5. 查看编译错误并跳转到代码位置。
6. 设置断点并执行调试。
7. 运行多组样例。
8. 执行对拍。
9. 保存并重新打开文件。

整个流程不得要求创建工程、连接网络、安装插件或使用云服务。

## 九、实施原则

不要一开始就同时开发所有插件和工程能力。

建议按以下顺序推进：

**第一阶段：明确核心边界。**

完成核心功能清单、运行模型、配置系统和单文件工作流定义，明确哪些能力属于核心，哪些能力必须通过插件扩展。

**第二阶段：验证核心架构。**

优先验证编辑器、编译运行、输入输出、测试、对拍、基础调试和自动恢复等基础能力，并建立性能与稳定性基准。

**第三阶段：建立插件基础设施。**

确定插件 API、元数据格式、生命周期、权限模型、故障处理和配置迁移机制。先用少量内部插件验证架构是否真正可用。

**第四阶段：逐步增加专业能力。**

根据用户需求和架构成熟度，逐步开发工程构建、语言服务、Git、专业调试、静态分析和远程开发等插件。

**第五阶段：持续验证统一产品体验。**

无论插件数量如何增加，都必须持续测试未安装插件的纯核心环境，确保启动速度、资源占用和单文件工作流没有发生不可接受的退化。

## 十、最终产品原则

整个产品始终遵循以下原则：

1. 只有一个 IDE，不分竞赛版和工程版。
2. 核心保持轻量、独立、离线可用。
3. 单文件 C++ 开发始终是核心工作流。
4. 核心功能完整，插件只负责扩展。
5. 插件按需安装、按需加载，不能拖累核心。
6. 插件系统必须具有明确的接口、权限、隔离和故障处理机制。
7. 工程能力可以逐步扩展，不要求一次性全部实现。
8. 不预置算法模板和算法代码片段。
9. AI 功能可选、可控，不替用户完成算法学习与解题。
10. 稳定性、可诊断性和实际性能优先于功能数量。

**产品的本质不是将一个庞大的工程 IDE 拆成许多插件，而是以轻量、完整的 C++ 核心为基础，建立一个能够长期扩展、同时不破坏原有体验的开发环境。**
