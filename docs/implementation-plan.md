# ccrIDE 产品边界与实施清单

核对日期：2026-11-07。依据：[用户提供的总体需求](product-requirements.md)。

本文区分当前实现与后续设计。表中的“部分”不代表已通过整体验收；后续模块、接口和目录均为设计约定，不代表已有实现。用户原文是产品要求，README 只描述实际行为。

## 1. 产品边界

只维护一个 IDE。无项目、无插件、无账户、无网络的单文件工作流必须完整。

| 属于核心 | 属于可选插件 |
|---|---|
| 编辑、高亮、补全、基础语法检查、基础导航与重命名 | clangd、完整跨工程语义分析与重构 |
| 单文件编译运行、输入输出、进程资源管理 | CMake/Make/Ninja/Bazel 与复杂多目标构建 |
| 样例、批量测试、测试点/Subtask、对拍 | 工程测试框架、覆盖率、专业质量分析 |
| 基础 GDB 调试、变量、调用栈、表达式求值 | 线程、寄存器、反汇编和复杂内存检查 |
| 自动保存、恢复、崩溃日志、配置、便携部署 | Git、依赖管理、远程与容器、嵌入式、性能工具、CI |
| 空的用户模板和片段管理工具 | 可禁用、可卸载、明确联网用途的 AI 辅助 |

不预置算法模板或算法片段。保留用户内容；迁移时不得删除用户已有模板。AI 已拆为可卸载 DLL 插件，但仍在主进程执行。详见 [架构核对与验收边界](architecture-review.md)。

## 3. 核心运行模型（架构契约，执行后端已落地）

`UI -> TaskCoordinator -> ExecutionService -> WindowsProcessBackend`。编译、运行、测试、对拍、GDB 及插件进程复用任务和执行基础设施，避免继续复制进程代码。

当前 execution::Run 已承接 Windows 执行后端与进程工具调用；TaskCoordinator、持久任务 ID、任务归档和上层测试/调试接口仍是后续工作，不能视为已完成整个模型。

### 3.1 执行输入与结果

- `ExecutionRequest`：任务 ID、可执行路径、结构化 argv、绝对 cwd、环境覆盖、stdin 来源、timeLimitMs、memoryLimitBytes、outputLimitBytes、归档目录。
- stdin 来源明确为交互、自定义文本、文件或样例；文件/文本发送完关闭写端，使目标收到 EOF。
- `ExecutionEvent`：状态、stdout、stderr、耗时、资源采样、诊断。每个事件带任务 ID 和序号；消息队列和每帧读取均有预算。
- `ExecutionResult`：启动结果、退出码、原始系统错误、耗时、观测峰值、结束原因、日志与产物路径。
- 执行层只给事实与终止原因；比较器将结果转换为测试判定。未启动成功不能被当成 RE；比较前必须确认正常结束。
- 状态为 queued -> starting -> running -> succeeded/failed/timedOut/memoryExceeded/outputExceeded/cancelled；终态只提交一次。
- 展示 argv 对应的实际命令、cwd、环境覆盖和限制。继承环境可按需查看，凭据脱敏，普通日志不默认倾倒整个进程环境。

### 3.2 Windows 执行边界

挂起创建进程，配置 Job，确认分配成功后再恢复。任一步失败即清理尚未运行的进程并报告系统错误，不静默降低进程树清理保证。继承句柄只包含本任务必要管道。

Job 使用 kill-on-close，并按能力配置进程/Job 内存限制；墙钟超时由协调器处理。正常主进程退出也关闭 Job 并回收后代。独立读写任务处理管道，避免 stdin 或连续输出阻塞取消；所有路径关闭句柄并等待回收。

显示截断、完整归档上限与强制 OLE 是不同设置；达到字节上限时停止任务并标记 OLE。单条无换行输出同样受限。清理失败必须记录；不能假称成功。异常码保留原值，并尽可能说明访问冲突、栈溢出等原因。

该模型用于可靠性与资源管理，不保证抵抗任意恶意原生代码；平台能力和失败边界需在界面、日志中可见。

## 4. 数据、配置与单文件工作流定义

后续配置加入 schemaVersion 与迁移记录。现有 settings.json 保持兼容，不因缺少新字段改变默认编辑体验。

目录解析顺序拟为：显式用户目录 -> 用户主动启用的便携目录 -> Windows 用户本地数据目录；只在明确的迁移流程读取旧 D/E/F 数据。迁移先备份、验证，不删除原内容，不静默覆盖个人配置。

逻辑数据分区：settings、recovery、sessions、templates、snippets、testcases、runs、plugins、logs。可写数据与安装资源分离；编译器/必要工具可随便携目录放置，配置支持相对便携根路径。保存错误必须反馈。

- 新建/打开 cpp -> 选用已发现或手动指定的编译器 -> 编译/运行/编译运行；不生成项目。
- 首次使用缺少工具时显示具体路径/原因与配置入口，不能只有无响应按钮。
- 运行面板切换输入来源，显示 stdout/stderr、耗时、退出原因、复制/保存入口。
- 测试面板管理样例与组，使用同一编译产物逐例执行；失败可定位差异与重放。
- 对拍面板指定三个文件，标签显示角色；先全部编译成功，再逐轮执行 gen -> sol/brute -> compare。
- 调试启动检查 gdb 路径、编译调试信息、握手与协议；独立会话/日志，失败不阻塞编辑保存。
- 所有标签周期恢复快照，区分已保存路径和未命名内容；恢复只创建可查看副本，不直接覆盖源文件。

测试数据记录 ID、分组、Subtask、输入、期望输出、启用状态、比较策略、限制与运行配置。比较默认策略必须显式展示，严格字节比较与空白宽松比较均可选，不能悄悄忽略差异。

对拍归档包含种子/轮次、输入、三程序版本或源码摘要、命令与配置、stdout/stderr、判定和耗时；生成器错误与解法错误分别标识。重放直接使用归档输入，不依赖重新随机生成。

## 5. 插件架构决定与迁移条件

采用混合架构：可信、轻量、非阻塞的受控 UI 扩展可以留在进程内；语言服务、耗时任务、AI 网络服务等优先进程外，由核心分配任务 ID、限制、取消和日志。第三方任意原生 DLL 不具有可靠的进程内隔离，不能标成受控安全插件。

新 API v1 显式定义版本协商、能力、结构尺寸/消息 schema、错误、线程约束、异步取消、资源释放与生命周期。避免跨 DLL 传 STL 对象。旧 PluginApi 不改名冒充稳定 v1，先设计兼容迁移并保留错误提示。

元数据包括 id/name/version/apiRange/platform/arch/dependencies/permissions/activationEvents/entry/resources。仅扫描和读取清单不触发初始化；enabled 与 loaded 分开。禁用先停止任务与服务再释放资源，升级通过暂存、验证、切换和回滚完成。

权限至少包括文件、进程、网络、凭据、后台任务、调试。核心代理检查操作与路径；缺少 OS 隔离时明确原生插件限制。AI 不直接读全工作区，发送范围由用户动作决定。配置迁移导出默认剔除凭据。

## 7. 验收与性能记录规范

干净配置、插件目录为空、断网，在同一安装中完成：打开 cpp -> 编译运行 -> 输入 -> 错误跳转 -> 断点调试 -> 多样例 -> 对拍 -> 保存重开。这是目标场景，当前尚未全部通过。

专项故障集：编译器/GDB 不存在、含空格和中文路径、非零退出/访问冲突/栈溢出、超时、内存耗尽、无限输出（含无换行）、stdin 不读取、主进程退出但后代驻留、停止与自然退出竞争、Job API 失败、恢复文件损坏/不可写、插件 API/依赖/架构错误、服务卡死/崩溃/耗尽资源、升级中断与回滚。

记录 OS、CPU、内存、磁盘、工具链、提交或构建摘要、配置、插件列表和测试数据集。分别记录冷启动、空闲工作集/私有内存与 CPU、大文件打开、首次编译运行和操作响应；多次测量报告分布。隐藏窗口渲染检查和逻辑测试不能替代真实冷启动/进程资源基准；没有测量前不填写性能达标数字。

每次交付附上构建、回归、UI 检查与故障测试的实际结果及未覆盖项。核心清单长期保留上述缺口，完成后再以可复验依据更新状态。
